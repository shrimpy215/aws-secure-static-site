The solution

What you're actually building

A static website where the S3 bucket has no public access at all — not restricted, not filtered, just off. CloudFront is the only entity on the internet that can read from it, and only because the bucket policy says so by ARN.

The site itself is deliberately simple. That's not the point. The point is the controls: every design decision has a reason grounded in threat modeling, and the README explains each one. That's what distinguishes this from a cloud lab.

Security decisions

Controls mapped to what they prevent

Each control below was a deliberate choice. The alternative was available — public bucket, OAI instead of OAC, no headers — and was rejected for a specific reason.

ControlImplementationWhat it prevents
S3 public access block All four block settings enabled Eliminates any path to accidental public exposure, even if a future bucket policy or ACL is misconfigured
Origin Access Control (OAC) SigV4 signing, always — scoped to this distribution's ARN Ensures no other CloudFront distribution, IAM principal, or anonymous request can read from the bucket
HTTPS enforcement redirect-to-https on CloudFront behavior Eliminates plaintext HTTP traffic; prevents protocol downgrade and credential interception
HSTS max-age=31536000; includeSubDomains Instructs browsers never to attempt HTTP for one year — defeats SSL stripping even before a redirect fires
X-Frame-Options DENY Blocks the page from loading inside any iframe — prevents clickjacking overlays on third-party sites
Content-Security-Policy default-src 'self' Restricts resource loading to the same origin — prevents injected scripts from calling out to attacker infrastructure
X-Content-Type-Options nosniff Stops browsers from MIME-sniffing a response — a file declared as text cannot be executed as script
Referrer-Policy strict-origin-when-cross-origin Limits referrer data sent to third-party sites — reduces information leakage on external navigation
S3 server-side encryption AES-256 (SSE-S3) Encrypts all objects at rest — a stolen storage volume or snapshot yields ciphertext, not content
S3 versioning Enabled Retains prior object versions — supports recovery from accidental deletion or content corruption
OAC vs OAI

Origin Access Identity (OAI) is the legacy mechanism for CloudFront-to-S3 authentication. Origin Access Control (OAC) replaces it with SigV4 request signing and supports AWS KMS-encrypted buckets — OAI does not. Using OAC is the current AWS recommendation and the correct choice for any new deployment.

Browser-level controls

Security headers in production

These headers are served by CloudFront on every response via a response headers policy — no changes to the HTML are required. Verified against securityheaders.com on deployment.

Strict-Transport-Security

Forces HTTPS for one year. Browsers won't attempt an unencrypted connection even if the user types http://. Defeats SSL stripping.

X-Frame-Options: DENY

Blocks the page from being embedded in any iframe on any domain. Prevents clickjacking — invisible overlays that trick users into clicking something else.

Content-Security-Policy

Allows resources only from the same origin. An injected script that tries to load from an external host gets blocked before it executes.

X-Content-Type-Options

Prevents MIME-type sniffing. A file served as text/plain cannot be reinterpreted as executable JavaScript by the browser.

Referrer-Policy

Sends only the origin (not the full URL) on cross-origin navigation. Limits information leakage when users follow external links.

Build sequence

Five stages

  1. S3 bucket complete
    Private bucket with AES-256 encryption, versioning enabled, all four public-access block settings on. No website hosting. No public ACL. The bucket has no idea CloudFront exists yet.
  2. CloudFront + OAC complete
    Distribution with Origin Access Control using SigV4 signing. redirect-to-https on the default cache behavior. Default CloudFront certificate. S3 bucket policy scoped to this distribution's ARN added at the same apply.
  3. Security headers policy complete
    CloudFront response headers policy with HSTS, X-Frame-Options, CSP, X-Content-Type-Options, and Referrer-Policy. Attached to the default cache behavior. Verified live with securityheaders.com — Grade A.
  4. Content upload and smoke test complete
    index.html uploaded via AWS CLI. CloudFront URL returns a 200, all headers present in curl output. Direct S3 endpoint returns 403 — confirming the bucket policy is working as intended.
  5. README and destroy complete
    README with architecture overview, security design decisions table, threat model, and deployment instructions committed to GitHub. terraform destroy run — all resources removed, cost impact: ~$0.

Positioning

What this proves

Project 1 establishes the baseline: infrastructure as code, a working deployment, and a README that explains security decisions rather than just listing resources. The S3 + CloudFront + OAC pattern is a standard AWS architecture — what's non-standard is being able to explain, in one sentence, why OAC replaced OAI, what the bucket policy condition actually enforces, and what attack each response header mitigates.

For a Solutions Consultant screen, it demonstrates Terraform fluency and secure-by-default infrastructure habits. For a Cloud Security Architect screen, the response headers section and the OAC explanation show that browser-level controls and origin authentication are understood as a system, not a checklist.

The paragraph that matters

The threat model entry for OAC — "a request directly to the S3 endpoint returns 403" — is worth being able to say out loud in an interview and then explain the three-line bucket policy condition that makes it true. That's the difference between having deployed the architecture and understanding it.
